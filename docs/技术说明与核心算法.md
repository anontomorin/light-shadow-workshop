# 《光影工坊：窗棂之间》技术说明与核心算法

本文档说明本项目（`light-shadow-workshop`）的核心算法，重点回答四个问题：

1. **窗棂是怎么生成的**（模板 → 杆件）
2. **镂空是怎么保留的**（凸块分解 + 逐块凸包 + mask 并集）—— 本项目的核心技术点
3. **同一个模型怎么支撑"关卡 / 实验室 / 工坊"三套玩法**（14 种形状、复合构件、10 关题目）
4. **显示与导出为什么不可能不一致**（同一条数据链路）

## 1. 数据模型：`WindowDocument` 是唯一真源

工坊的一切（3D 预览、墙面影子、读数、海报、存档）都从同一个纯 JSON 文档派生：

```ts
interface WindowDocument {
  schemaVersion: 1;
  id: string;  name: string;  author?: string;
  patternId: PatternKind;          // 'step-step-brocade' | 'ice-crack-style'
                                   // | 'three-cross-six-bowl-diamond' | 'huiwen-border'
                                   // | 'blank' | 'custom'
  width: number; height: number;   // 窗格整体尺寸（世界单位）
  frameWidth: number;              // 外框棂条宽度
  barWidth: number;                // 内部棂条宽度
  depth: number;                   // 杆件厚度（Z 方向）
  strokes: LatticeStroke[];        // 全部笔画（模板 + 用户自绘）
  parameters: PatternParameters;   // 生成参数（行列数、种子、密度…）
  createdAt: string;  updatedAt: string;
  isUserCreation?: boolean;
}

interface LatticeStroke {
  id: string;                      // 'f0'..'f3' 外框 / 'h0' / 'v1' / 'c12' / 't3' / 'f7' / 'u0'
  role: 'frame' | 'lattice' | 'border';
  width: number;
  source: 'template' | 'user';
  points: { x: number; y: number }[];   // 窗格局部坐标，原点在窗心
}
```

**设计要点：**

- 坐标原点在窗心（不是左上角），因此"把窗放平/旋转"只是换一个矩阵，不改文档。
- 模板与自绘用**同一个 `strokes` 数组**承载，`source` 字段区分。这样投影、统计、导出只需一套代码。
- 模板参数变更时走 `regenerateDocument(doc, nextParams)`：重新生成模板笔画，并把**用户自绘的笔画按宽高比例缩放**保留下来（换模板不丢创作）。

### 1.1 生成器与参数夹紧

`GeometryLimits.ts` 里所有参数都有硬区间，`clampPatternParameters()` 统一夹紧：

| 参数 | 区间 | 说明 |
|---|---|---|
| `width` / `height` | 1.6–5.0 / 2.2–7.0 | 窗格尺寸 |
| `frameWidth` | 0.06–0.5 | 且强制 `2·frameWidth < min(width,height)` |
| `barWidth` | 0.04–0.34 | 内部棂条宽度 |
| `depth` | 0.12–0.6 | 杆件厚度 |
| `rowCount` / `columnCount` | 1–7 / 2–7 | 分格数 |
| `density` | 0.35–1 | 冰裂纹保留内部线段的比例 |
| `seed` | 有限整数 | 同种子输出完全一致 |
| `borderRepeat` | 3–8 | 回纹每边重复次数 |

**复杂度硬上限**（`COMPLEXITY_LIMITS`）：`maxStrokes 120`、`maxSegments 400`、`maxPointsPerStroke 64`；用户自绘另有更紧的上限（40 笔 / 40 点 / 120 段）。`inspectComplexity()` 会在超限前给出提示并拒绝继续增加，**不会**让浏览器卡死。

> 关于 `maxSegments`：最初按文档中的建议值定为 320，但"全部 5 个模板 + 回纹边饰 + 最大行列"这一最坏组合实测为 **324 段**，会被误判超限。因此按文档给出的区间上界调整为 **400**，并在 `verify:window` 里断言最坏组合仍在上限内（当前实测最大 324/400）。

### 1.2 三种模板的几何构造

- **步步锦式**（`StepStepPattern.ts`）
  外框 4 根 → `rowCount-1` 根横棂 + `columnCount-1` 根竖棂 → 在每个格心按 `(行+列)` 奇偶交替加入一段"阶梯"折线（内缩量 `d = 0.3·min(格宽, 格高)`）。构造上等价于"矩形格网 + 交错阶梯"，镂空是规则方格。
  `variant: 'plain'` 可只保留基础格网。

- **冰裂纹式（风格化）**（`IceCrackPattern.ts`）
  在 `cols × rows` 的网格顶点上施加固定幅度抖动（`JITTER = 0.17`，**边界顶点不抖动**，保证窗心轮廓整齐）；候选边 = 全部网格边（边界边恒保留）+ 每个格的一条对角线；按 `rng() <= density` 决定是否保留，用 mulberry32 种子随机数保证可复现。因为没有两条完全平行的长线，视觉效果接近"冰面开裂"。
  同 `seed` → 逐点一致；换 `seed` → 不同构图（`verify:window` 两条断言分别验证）。

- **三交六椀菱花式（数字示意）**（`LiuwanLinghuaPattern.ts`）
  三个方向的等距线族：0°、60°、120°（步长 `d = s·√3/2`），裁剪到窗心矩形；三者相交形成三角形—菱花形格网。再在三角格点 `(x = d(kk − 2mm)/√3, y = kk·d)` 放置简化的**六边形花心**（半径 `r = min(s·0.2, 0.42)`，总数上限 40），对应"交点装饰成花心"的形态描述。
  界面与卡片上都标注 **「数字示意」**，不声称复原具体文物。

- **回纹边饰**（`HuiwenBorder.ts`，辅助模块）
  一个归一化的"回"字折线单元，沿外框四条内边重复绘制，重复次数由 `borderRepeat` 控制。它是**叠加层**：勾选后会在当前模板之上追加回纹笔画（`generatePatternStrokes` 里做 id 去重）。

## 2. 核心算法：凸块分解 + 逐块凸包 + 并集

### 2.1 问题

最朴素的做法是把一个物体的**全部**投影点交给 `convexHull()` 求一次凸包，得到一个多边形。

这对实心凸形状（方块、三角、圆盘、六边形…）是正确的，但对任何**有凹陷或有孔洞**的形状彻底失效：

```
十字形      → 整块凸包把四个凹角抹平，影子变成一个实心方块
五角星      → 整块凸包把五个星角之间的内凹抹平，影子变成一个五边形
圆环        → 整块凸包把中间的孔填死，影子变成一个实心圆
一扇花窗    → 整块凸包把所有窗格空隙填死，影子变成一块实心窗板
```

这不是"不好看"的问题，而是**判定层面的致命错误**：目标轮廓是有孔的，玩家永远匹配不上一个无孔的实心块。
更隐蔽的是——它**看起来仍然"有影子"**，如果只断言"影子非空"，这种错误实现照样能通过测试。

### 2.2 语义：什么是"一个物体的轮廓"

本项目的定义是：

> 物体 = 若干**凸块**的并集（`ShapePart[]`）；
> 轮廓 = 各凸块**各自**的投影凸包的并集。

凸包只在**单个凸块内部**求，所以：

- 凸块内部的重叠被并集消掉 → 交叉处是实心、没有接缝、不会双重加深；
- 凸块之间的凹陷/孔洞没有任何多边形覆盖 → 掩码恒为 0，**如实保留**。

`convexHull()` 的调用契约就写在函数注释里：**只对单个凸块调用**。这让"凹形"变成"分解问题"而不是"算法问题"。

### 2.3 14 种形状的凸块分解（`src/scene/GeometryFactory.ts`）

| 形状 | `ShapeType` | 凸块数 | 分解方式 |
|---|---|---|---|
| 三角形 | `triangle` | 1 | 单一凸多边形 |
| 正方形 | `square` | 1 | 同上 |
| 长方形 | `rectangle` | 1 | 同上 |
| 圆形 | `circle` | 1 | 48 边形（内接，视觉等价） |
| 六边形 | `hexagon` | 1 | 正六边形 |
| 菱形 | `diamond` | 1 | 旋转 45° 的方形 |
| 五边形 | `pentagon` | 1 | 正五边形 |
| 八边形 | `octagon` | 1 | 正八边形 |
| 梯形 | `trapezoid` | 1 | 等腰梯形（仍为凸） |
| 半圆 | `semicircle` | 1 | 圆弧 + 直径围成的凸多边形 |
| **十字形** | `cross` | **3** | 竖臂 + 左臂 + 右臂三个矩形，**互不相交**，并集恰为十字形 |
| **五角星** | `star` | **6** | 中心内五边形 + 5 个外三角；**内五边形的边就是星形的真实凹边界** |
| **圆环** | `ring` | **18** | 18 个凸环扇块（割线多边形近似，面积误差 < 0.5%） |
| 棂条 | `slat` | 1 | 矩形；工坊里则逐个杆件拆分 |

分解的**正确性**不是靠目测：`verify:window` 断言"每个凸块自身都是凸的"（`convexHull(p)` 的面积必须等于 `p` 的面积），
14 种形状全部通过。五角星的 5 个外三角与内五边形共用边，因此并集既不会留缝、也不会把内凹填掉。

### 2.4 复合构件：一个物体可以有很多零件

`ShadowObjectDefinition` 除了单一 `shape`，还可以给出 `parts: ShapePart[]`：

```ts
export interface ShapePart {
  shape: ShapeType;
  dx?: number; dy?: number;   // 面内平移（物体局部坐标）
  rot?: number;               // 面内旋转（度）
  w?: number; h?: number;     // 目标宽高（物体局部单位）
}
```

- `w` / `h` 是**按图纸写法**的目标宽高，内部经 `getShapeBaseSize(type)` 换算成缩放系数；
  只给一个轴时按等比例缩放。基准尺寸对**旋转对称形状**（三角/圆/六边/五边/八边/星/环）取**外接圆直径**，
  其余取包围盒，这样 `w = h` 一定意味着等比。
- 一个零件也可以只给 `shape` 不给 `w/h`，此时直接用基础尺寸。

工坊的窗棂是同一模型的另一种特例：**每一根杆件就是一个凸块**（`WindowProjector.extractBars(doc)`），
所以"窗棂逐杆件投影"和"关卡逐零件投影"是**同一段并集代码**。

### 2.5 完整数据链路

```
物体定义（ShapeType 或 ShapePart[]）
   │  GeometryFactory.getObjectLocalVertices(def)   每个凸块一组局部顶点（前后两层）
   ▼
THREE.Vector3[][]（每组局部顶点）
   │  projectParts(parts, transform, light, scale, WALL_Z)
   │    对每个凸块：
   │      每个顶点：applyMatrix4(matrixWorld) → projectPoint(light, world, WALL_Z)
   │                 t = (Lz − Zw) / (Lz − Pz)；Qx = Lx + t·(Px − Lx)
   │      barGap < MIN_LIGHT_GAP  →  跳过该凸块（避免镜像伪影子）
   ▼
   │      convexHull()   ← 关键：只在单个凸块内部求凸包
   │      clipPolygonToWall()   ← Sutherland–Hodgman，裁到 18×10 墙面
   ▼
Point2[][]（N 个多边形，N ≥ 凸块总数）
   │  SilhouetteRasterizer.rasterize(polygons)   ← 并集：像素落在任意一个多边形内即为 1
   ▼
二值掩码 288×160  →  IoU 判定 / 读数 / 墙面渲染 / 海报
```

关键代码（节选，`WindowProjector` 的逐杆件版本，与 `projectParts` 同构）：

```ts
for (const bar of bars) {
  const projected: Point2[] = [];
  let barGap = Infinity;
  for (const local of barLocalVertices(bar)) {
    const world = local.clone().applyMatrix4(matrixWorld);
    barGap = Math.min(barGap, light.z - world.z);      // 该杆件到光源的最近深度
    const q = projectPoint(light, world, wallZ);
    if (q && Number.isFinite(q.x) && Number.isFinite(q.y)) projected.push(q);
  }
  if (barGap < MIN_LIGHT_GAP) { failedBars++; continue; } // 太贴光源：跳过，避免镜像伪影子
  if (projected.length < 3)   { failedBars++; continue; }
  const hull = convexHull(projected);                     // ← 单凸块凸包
  const clipped = clipPolygonToWall(hull);
  if (clipped.length >= 3) { polygons.push(clipped); projectedBars++; }
}
```

**深度安全（`MIN_LIGHT_GAP = 2.0`）**：当某个凸块与光源在 Z 上过于接近时，`t` 会爆掉，产生无穷放大或镜像的伪影子。
这里用**每个凸块各自**的 `barGap` 判断（早期版本误用了一个全局最浅深度，导致合法杆件被连坐跳过），
只跳过真正越界的那一块，并给出可读提示：

> 「部分构件离光源过近（安全余量需 ≥ 2），墙上显示的是不完整轮廓。」

## 3. 显示与判定为什么不可能不一致

### 3.1 双路径逐点比对

代码里同时存在两条投影路径：

| 路径 | 用途 | 数据来源 |
|---|---|---|
| 解析式 `projectParts(localParts, transform, light)` / `projectWindowBars(bars, matrix, light)` | 纯函数，Node 可直接测 | `getObjectLocalVertices(def)` / `extractBars(doc)` 的解析顶点 |
| 渲染路径（遍历真实 Mesh） | 屏幕上真正画出来的 | `mesh.geometry.attributes.position` + `mesh.matrixWorld` |

之所以能一致，是因为**渲染用的顶点本身就是解析式算出来的**：所有凸块共享一份缓存的挤出/盒体几何
（键为 `type#index`），通过 `position` / `rotation.z` / `scale` 摆放。three 的局部矩阵是 `T·R·S`，
所以 GPU 实际看到的角点恰好等于解析式算出的同一组值。

### 3.2 比对方式为什么是"点集 + 掩码 IoU"

第一版断言的是"凸包顶点序列逐点一致"，结果第 10 关（含 18 段圆环零件）报不一致。
逐项排查（临时探针打印每个零件的 z 与去重后的 XY）后确认：

1. **解析顶点完全正确**——同一零件两条路径的世界 z 与去重后的 XY 完全相同；
2. 差异只有 ~4e-8，来源是挤出几何在**端面三角化与侧壁处会输出重复顶点**，而解析式每个点只出现一次；
3. 薄环扇块上常有三点近似共线，`convexHull` 的成员判定会在 1e-7 量级翻转。

这是**数值噪声，不是投影算错**。因此改成语义更贴切、也更严格的写法：

```ts
// 逐零件：去重后做点集比对
dedupePoints(analyticPart, 1e-5)  ≟  dedupePoints(meshPart, 1e-5)   // 4 关 / 60 个零件全部一致
// 整体：掩码级 IoU
computeIoU(analyticMask, meshMask) >= 0.9995                        // 4 关全部通过
```

再加上"多边形数量一致"与"包围盒一致"（4.291188×6.168582）作为粗粒度旁证。

### 3.3 双路径的边界与已知限制

- 解析式路径要求构件必须是"轴对齐盒体 + 单轴（面内）旋转"。一旦引入**绕 X/Y 的零件自身旋转**或非盒体截面，
  式子就不再精确，两条路径会分叉。当前窗格整体旋转是通过 `matrixWorld` 施加的（两条路径都吃这个矩阵），
  零件自身的 `rot` 也是面内旋转，所以不受影响。
- **凸块必须真是凸的**：单块内部用凸包是精确的。若将来引入凹截面（如弧形棂条），
  要么继续拆凸块，要么改用凹多边形三角化。当前 14 种形状与自绘笔画都满足这个前提，
  且 `verify:window` 会断言"每个凸块的凸包等于自身"。

## 4. 墙面渲染：模板缓冲并集（`ProjectionRenderer`）

墙面上的影子不是一张贴图，而是**真实的投影多边形**被画成 three 的 Mesh：

- 所有投影多边形先被三角化，作为"印章"写进**模板缓冲**（`stencilRef = GROUP_SHADOW`）；
- 然后用一个覆盖整个墙面的平面，设置 `stencilFunc = EqualStencilFunc` + `stencilRef = GROUP_SHADOW`，只在被印章标记过的像素上着色。

这样重叠的多边形影子**只被铺一次色**，颜色完全均匀 —— 这就是 e2e 里"重叠区域颜色均匀（无叠加接缝）"那条断言的物理来源（实测 `distinct = 2`，接近理论最优值 1）。

多层零件的另一面是**多边形数上升**：关卡影子多边形数从 1–6 升至 1–26（第 10 关 26 个），
实验室 13 种形状里圆环一个就贡献 18 块。实测（`wallShadowCount()`）：第 7/8/9/10 关分别为 **10 / 14 / 9 / 26**，
全部大于各自的物体数（3/3/3/4），这本身就是"每个构件被拆成多个凸块独立投影"的现场证据。

**层序（谁压在上面）**由 `renderOrder` 显式钉死，而不是靠 z 或加入顺序：

```
目标淡填充(+0.01) → 目标描边(+0.02) → 影子(+0.04，最上)
```

原因：three 会把 `transparent: true` 的对象放进透明通道**按相机距离排序**，而墙上的薄片 z 只差 0.01–0.04，换算成相机距离差不到 0.03，几个对象经常算出**完全相同**的 camDist，排序不稳定 → 层序随机翻转（曾因此出现"影子有时在上有时在下"）。`depthWrite` 只影响不透明通道内部，对透明印章无效，不是解法。
`layerOrder()` 因此直接断言 `renderOrder`，而不是做像素采样（物体本体会挡住自己的影子，像素探针不可靠）。

## 5. IoU 判定与三套玩法共用一条链路

- **IoU（`SilhouetteMatcher.computeIoU`）**：交集像素 / 并集像素，输入是两份同尺寸二值掩码。
- **通关契约未放宽**：`REQUIRED_CONSECUTIVE_HITS = 3`、存档 schema、解锁与计分逻辑一律未改；
  前 6 关的关卡数据、目标参数与阈值（0.79–0.83）**原样保留**。
- **投影入口统一**：关卡（`LevelManager`）、实验室（`LabSession`）、工坊（`WorkshopController`）
  现在都走同一个 `projectParts()`，只是喂进去的凸块来源不同（形状分解 / 杆件分解）。
  这也是为什么"改了核心算法，旧 6 关仍然零回归"能成立：它们的几何没变、公式没变，只是从
  "整物体一次凸包"换成"单凸块一次凸包"——而它们本来就是凸形状，两者结果**恒等**。
- **新增关卡（7–10）的阈值按实测可达性标定**，见 README 第六节与《测试报告》第三节：
  细长棂条的轮廓对角度误差远比实心方块敏感（实测精对齐只到 0.734–0.778），
  若强留 0.83 会变成**不可达**。四条硬约束（粗对齐 < 通关阈值 ≤ 离散控件可达、精对齐 ≥ 大师阈值、目标 IoU ≈ 1.0）
  在 10 关上全部成立。
- 工坊与关卡/实验室**共用**同一个 `SceneManager` / `WebGLRenderer` / `SilhouetteRasterizer`，只通过接口适配接入：

```ts
// src/gameplay/InteractionController.ts
export interface InteractiveStage {
  getPickables(): THREE.Object3D[];
  setSelected(id: string | null): void;
  getSelected(): string | null;
  updateTransform(id: string, t: Transform3D): void;
}
```

`StudioScene`（关卡/实验室）与 `WorkshopStage`（工坊）都实现这个接口，因此 `InteractionController` 的拖动、拾取、高亮逻辑**一份代码两处复用**，不需要为工坊另写一套交互。

在 `StudioScene` 里，一个物体现在是一个 `THREE.Group` + N 个零件 Mesh，`getPickables()` 返回**所有零件 Mesh**，
每个 Mesh 的 `userData.objectId` 指回物体 id，因此点中任何一个零件都会选中整个物体。

在工坊里，`transformsForAllStrokes()` 让**每一根杆件的 id 都映射到同一个整窗变换**，`updateTransform()` 写的是整窗的位移/旋转，因此拖动窗格时所有杆件一起走。

## 6. 关卡题目：花窗构件工具箱

第 7–10 关的题目不是贴图，而是用 `src/data/levels.ts` 里的**构件工具箱**拼出来的复合物体：

```ts
slat(w, h)                        // 一根矩形棂条（h > w 即为竖直棂）
rhombus(w, h)                     // 一个菱形（旋转 45° 的方块）
frame(halfW, halfH, t)            // 四面外框，由 4 根棂条组成
rosette(coreW, coreH, ringR, petalW, petalH, count = 6, startDeg = 30)
                                  // 花心：中心一圈 + 外围花瓣
```

| 关卡 | 题目 | 构件组成 | 物体 / 凸块 | 阈值（通关/优秀/大师） |
|---|---|---|---|---|
| 7 | 方格窗 · 十字棂 | `frame(3.0, 2.2, 0.28)` + 十字棂（2 根）+ 四角菱花（4 个） | 3 / **10** | 0.69 / 0.72 / 0.75 |
| 8 | 菱花窗 · 三交六椀 | `frame(3.0, 2.4, 0.3)` + 三交棂（0°/60°/120°）+ `rosette(...)` | 3 / **14** | 0.69 / 0.72 / 0.74 |
| 9 | 冰裂纹 · 碎影 | `frame(2.9, 2.3, 0.26)` + 主裂 3 根 + 副裂 3 根 | 3 / **10** | 0.67 / 0.70 / 0.72 |
| 10 | 窗棂总成 · 圆光窗 | `frame(3.2, 2.5, 0.32)` + 井字格（2 根）+ 菱格（2 根）+ `ring`（圆环） | 4 / **26** | 0.70 / 0.73 / 0.76 |

所有目标变换都用同一个反算公式摆位：给定"期望的影子中心"，反推物体位置。

```
t = 14 / (14 − z)        // 光源 z = 14
z = 4  →  t = 1.4        // 影子比物体放大 1.4 倍
place(light, shadow, z, rot) = 反推物体中心与朝向
```

这样"题目想要什么形状"和"玩家摆到哪里"用的是同一套几何，**不存在"目标轮廓是另外画的一张图"**。

四关的**格眼被如实保留**由 `verify:window` 逐关断言（孔洞数 2 / 4 / 9 / 12，见 §2.6）。

## 7. PNG 海报的数据路径

导出**不复用 WebGL 画布的像素**（否则会受相机角度、分辨率、抗锯齿、设备差异影响），而是走一条纯 Canvas 2D 的确定性管线：

```
renderPoster(input)
├── 左panel：drawDesign()   ← extractBars(doc) + barPlanCorners()  // 用杆件平面角点画设计图
├── 右panel：drawShadow()   ← input.polygons                       // 与墙面**同一份**多边形数组
│              失败兜底：drawMaskFallback()  ← input.mask          // 与 IoU 判定**同一份**掩码
└── 页脚：实时读数（镂空率 / 包围盒 / 面积，来自 computeMetrics）
```

**关键点：海报用的是 `this.polygons` 与 `this.mask`，也就是驱动墙面渲染和 IoU 判定的那两个对象本身**（不是重新算一遍）。所以海报上的窗影与屏幕上的影子、与判定用的掩码，三者数学上必然一致。

`drawShadow()` 把全部多边形塞进**一条** canvas path 后按 nonzero 规则 `fill()` 一次，效果等价于模板缓冲并集 —— 重叠处同样只被填一次色。

- 尺寸：`POSTER_WIDTH = 1920` / `POSTER_HEIGHT = 1080`
- 输出：`canvas.toBlob('image/png')` → `URL.createObjectURL` → 触发下载 → **4 秒后 `URL.revokeObjectURL`**（避免内存泄漏）
- 兜底：若多边形数组为空（例如全部杆件因深度非法被跳过），自动改用二值掩码放大绘制，保证导出永远不是一张空图。

### 9.4 工坊版面：操作区优先

工坊是"创作工具"，不是"关卡画面"，所以版面的第一约束是 **三维操作区必须居中且尽可能大**：

```
.workshop-screen   grid: auto / minmax(0,1fr) / auto    ← 工具栏 · 主体 · 操作坞
.workshop-body     grid-template-areas: 'left stage right'
                   grid-template-columns: var(--col-left) minmax(0,1fr) var(--col-right)
```

- 列宽写成 CSS 变量，`.workshop-body[data-collapsed~='left'|'right']` 把变量归零并 `display:none` 掉面板，
  画布立刻铺满整行（1600px 视口实测：三栏 968px → 全部收起 1556px）。
- 画布上叠一层 `.stage-hud`：左上「操作指引」卡（四步上手 + 全量键位表）、右上侧栏开关、底部状态条。
  状态条常驻显示位置 / 深度 / 影子尺寸 / 镂空率，**收起右栏后仍然读得到关键读数**。
- 工具栏从绝对定位改回网格流：`.game-topbar` 原本是 `position:absolute`，
  会让主体从 `y=0` 开始，画布上沿被工具栏盖掉约 69px。

**踩过的坑（值得记下来）**：`src/styles/screens.css` 里有一条为关卡 / 实验室页写的通用规则

```css
.stage-wrap { grid-column: 1; grid-row: 1; }
```

工坊的 `.stage-wrap` 同样命中它。结果画布被钉死在第 1 列（252px），而**左栏因为自动排布落到
了 `1fr` 的 940px**——看上去就像"操作区被挤到左上角一条窄缝，模板列表占了中间"。
`grid-column` 的显式定位优先级高于自动排布，所以只要还有一个元素被显式放进第 1 列，
自动排布就会把后续元素推到第 2 列，宽度随之互换。

修法是给工坊主体改用 `grid-template-areas` + `grid-area`，选择器比通用规则更具体
（`.workshop-screen .stage-wrap`，0,2,0 > 0,1,0）且 `grid-area` 会同时重置 `grid-column / grid-row`。

> 教训：**共享的布局原子类（`.stage-wrap` / `.side-panel` / `.game-dock`）一旦在多套网格里复用，
> 单靠自动排布是靠不住的**；每套网格都应该显式声明自己的区域，测出来（`getBoundingClientRect`）
> 而不是"看着差不多"。

### 9.5 自绘棂条：两个真实 bug 的复盘

这两个问题都是"看起来是手抖，其实是逻辑/样式缺陷"，记在这里避免重犯。

**① 进得去、出不来（`DrawingTool.enabled` 闸门卡死）**

`WorkshopController.onToggleDraw()` 的退出分支当时只做了：

```ts
this.drawing.finish();
this.setDrawMode(false);   // 关浮层、恢复交互
// ← 少了 this.drawing.disable()
```

`finish()` 调用的 `cancel()` 只清空折线，**不改变 `enabled`**。于是 `drawing.isEnabled` 永远停在
`true`，三处后果全都对得上用户的描述：

| 症状 | 原因 |
|---|---|
| 按钮一直显示「结束绘制」，点了没反应 | 按钮文案由 `state.drawing = drawing.isEnabled` 推导 |
| 点画布还想加点，节点却看不见 | `.stage` 的 pointerdown 监听仍在且 `enabled=true`，而浮层已被 `setDrawMode(false)` 隐藏 |
| 窗格再也点不中，左键只能转视角 | `WorkshopController.hitTest()` 首句 `if (!this.entered \|\| this.drawing.isEnabled) return false` |

修法是**只留一条退出路径**：`exitDrawMode()` 内依次 `drawing.disable()` → `setDrawMode(false)` →
提示 → `render()`，按钮与 Esc 都走它。同时把 Esc 做成渐进行为：折线上有节点时取消折线，
折线为空时通过 `onRequestExit` 退出整个绘制模式（此前按 Esc 永远只是清空折线，也会给人
"退不出去"的观感）。

**② 预览画在自己的 viewport 之外（替换元素的 `inset: 0` 拉伸不成立）**

`.draw-overlay` 是 `<svg>`。CSS 只写了 `position: absolute; inset: 0`，看似会撑满容器，
但 **`<svg>` 是替换元素**：`width: auto` 会退回内联默认尺寸 **300 × 150**，并触发
"绝对定位 + 替换元素"的过约束规则（右/下 inset 被忽略）；再加上 SVG 根元素默认
`overflow: hidden`，凡是画在这 300 × 150 之外的图元都会被自己的 viewport 裁掉。
窗格位于画布中部（远超 300 × 150），所以**节点和折线一直是不可见的**——不是"画得不好看"，
是一笔都没显示出来。

修法：显式给 `width: 100%; height: 100%; overflow: visible`，并在 e2e 里断言
浮层矩形 == 画布矩形（这条断言如果不写，下次改版面还会静默回归）。

> 教训：绝对定位的**替换元素**（`svg` / `img` / `video` / `canvas`）不要只靠 `inset: 0` 拉伸，
> 必须显式声明 `width` / `height`。

**顺带把"预览"做完整**（原来只有一条连线）：

```
绘制浮层（自下而上）
  .draw-frame       绘制范围虚线框 —— 明确"现在处于绘制模式"
  .draw-ghost       真实粗细的棂条预览：stroke-width = barWidth 换算到屏幕的像素数
  .draw-preview     节点之间的中心折线
  .draw-rubber      最后一个节点 → 光标的橡皮筋（还没点下去就能看到下一段）
  .draw-hover-dot   光标落点 + 吸附后的窗格坐标文字
  .draw-node-layer  每个节点：序号 + 圆点；起点用碧玉色；
                    当前节点额外画光晕（CSS 动画）与十字准星
```

`barWidth` → 屏幕像素不做假设，而是实测：把 `(0,0)` 与 `(barWidth,0)` 两个窗格局部坐标各
投影一次，取两点屏幕距离（`drawBarPx()`），因此视角、缩放、透视变化下预览粗细始终与最终
生成的棂条一致。另外**悬停与落点是两条回调**：`onHover` 每帧都会触发，只更新浮层；
`onPreview` 只在节点增减时触发，才走整块 HUD 重绘——避免为了鼠标移动把右栏读数、文化卡片
一起重算。

## 10. 性能与工程约束

- **顶点预算（工坊）**：所有杆件共享同一份 `BoxGeometry(1,1,1)` 与同一份 `WindowMaterials`，换模板只重建 Mesh 的 `scale/rotation/position`，不新建几何与材质。
- **顶点预算（关卡 / 实验室）**：零件几何按 `type#index` 缓存（`partGeometryOf`），同一种形状的所有物体共用同一份 `ExtrudeGeometry`；材质按物体各一份。`disposeGeometryCache()` 统一释放。
- **多边形数上限**：复合构件使影子多边形数从 1–6 升至 1–26，仍远低于光栅化瓶颈（288×160 掩码一次填充）。圆环的段数由 `RING_SEGMENTS = 18` 控制，可调。
- **重建时机**：投影只在脏标记为真时重算；`GameApp.onFrame` 中关卡与工坊的脏标记都带 `this.screen` 守卫。
- **动态导入**：`WorkshopStage` 通过动态 `import()` 懒加载（构建产物里是一个独立的 `WorkshopStage-*.js` 小块），不进入首屏关键路径。
- **释放**：`disposeWindowGroup` / `disposeWindowMaterials` / `disposeSharedBarGeometry` / `disposeGeometryCache` / `DrawingTool.dispose` / `WorkshopController.dispose` 显式释放 geometry、material、事件监听与 RAF。
- **生产安全**：`installDebugHook()` 首句即 `if (!import.meta.env.DEV) return;`，生产构建中 `window.__lightShadow` 不存在（由 `npm run verify:prod` 在真实 `dist` 上断言：10 / 10 通过）。
